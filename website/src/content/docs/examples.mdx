beryl ships four runnable example applications in the
[`examples/`](https://github.com/tylerbutler/beryl/tree/main/examples)
directory. They use a Gleam/BEAM backend with browser frontends that exercise
different realtime collaboration patterns.

They also demonstrate both of beryl's layers, deliberately. **Showcase** is the
multi-namespace app, so it uses the [channel layer](/guides/channels/). The
three focused servers each own a single topic family, so they stay on
[raw app-side dispatch](/guides/dispatch/) — the comparison is the point. See
[Choose an API](/choosing-an-api/).

<Aside type="caution" title="Pre-1.0 Software">
beryl is not yet 1.0. The API is unstable and features may be removed in minor releases.
</Aside>

## Showcase

**Source**: [`examples/showcase`](https://github.com/tylerbutler/beryl/tree/main/examples/showcase)

One socket runtime and three topic families, composed with
[`beryl_channels`](/guides/channels/). The cursors, chatrooms, and collab-docs
behaviors are each a channel handler registered on one socket system — no
socket-wide model and no hand-written router.

```bash
cd examples/showcase
gleam run
# Open http://localhost:8000
```

### What it demonstrates

| beryl feature | How it's used |
|---|---|
| **Channel composition** | One `beryl_channels.start` handler table owns `cursor:*`, `room:*`, and the `document:` prefix, matched in registration order |
| **Per-channel state** | Each joined topic keeps its own private state; the layer prunes it on close |
| **Lifecycle actions** | Presence tracking rides along with the join accept; the departure message and post-leave roster are termination actions |
| **Per-pattern rate limits** | `with_topic_rate` gives cursors, chat, and docs different limits |
| **Shared presence** | One presence actor is reused across the embedded apps that need it |
| **Single WebSocket endpoint** | Every embedded app shares `/socket/websocket` |
| **Cross-topic publishing** | The one genuinely cross-topic announcement (`lobby` room list) goes through a small actor holding the `beryl.Sockets` handle — the layer's `Endpoint.broadcast/3` |

### Architecture

```
Browser (Phoenix JS clients across /cursors, /chat, /docs)
  │  WebSocket (Phoenix wire protocol)
Server (Gleam)
  ├── Mist HTTP — serves the landing page and each example UI
  ├── beryl_channels — handler table owning cursor:*, room:*, document:
  ├── per-channel state — private to each joined topic
  ├── beryl presence — shared across cursors and chat
  └── groups + doc store — example-specific state
```

## Collaborative Cursors

**Source**: [`examples/cursors`](https://github.com/tylerbutler/beryl/tree/main/examples/cursors)

Move your mouse and see everyone else's cursor in real time. Open the app in
multiple browser tabs to try it.

```bash
cd examples/cursors
gleam run
# Open http://localhost:8000 in multiple browser tabs
```

### What it demonstrates

| beryl feature | How it's used |
|---|---|
| **App-side dispatch** | One topic family, so `standalone_update` routes every `cursor:*` join and message directly |
| **Topic wildcards** | `cursor:*` matches any cursor room |
| **Presence (CRDT)** | `PresenceTrack` + `BroadcastPresence` keep the `presence_list` current |
| **`BroadcastFrom`** | Fans out cursor moves to all *other* clients, excluding the sender |
| **Rate limiting** | `beryl.with_message_rate(per_second: 30, burst: 60)` throttles high-frequency cursor events |
| **WebSocket transport** | `mist_transport.upgrade` handles Phoenix-compatible WebSocket requests |
| **Phoenix JS client** | Frontend uses the official `phoenix` package over the standard wire protocol |

### Architecture

```
Browser (vanilla JS + Phoenix JS client)
  │  WebSocket (Phoenix wire protocol)
Server (Gleam)
  ├── Mist HTTP — serves HTML + static files
  ├── beryl app-side dispatch — cursor:* routing in update
  ├── beryl presence — CRDT-backed user tracking
  └── beryl BroadcastFrom — cursor position fan-out
```

## Chat Rooms

**Source**: [`examples/chatrooms`](https://github.com/tylerbutler/beryl/tree/main/examples/chatrooms)

A multi-room chat app with authentication, join rejection, typing indicators,
and message acknowledgment.

```bash
cd examples/chatrooms
gleam run
# Open http://localhost:8001?token=beryl-demo in multiple browser tabs
```

### What it demonstrates

This demo is designed to complement the cursors example by covering a different
slice of the beryl API:

| beryl feature | How it's used |
|---|---|
| **`on_connect` auth** | Token query param validated before the WebSocket upgrade is accepted |
| **`RejectJoin`** | Rooms reject joins when full (20 users max) or when the room doesn't exist |
| **`ReplyOk`** | Delivery of `new_msg` is confirmed on the client's push ref |
| **Reply payload validation errors** | Empty messages return `{code: 422, error: ...}` on the same push ref |
| **Groups** | Three rooms (`general`, `random`, `help`) are organized in a named group |
| **Presence typing** | `PresenceTrack` updates typing metadata and `BroadcastFrom` fans out typing indicators |
| **System messages** | Join/leave notices broadcast via `socket.Broadcast` |
| **Multiple topics** | One topic family (`room:*`), routed by one app-side `update` |
| **Rate limiting** | `with_join_rate` (5/sec, burst 10) and `with_channel_rate` (10/sec, burst 20) |

### Architecture

```
Browser (vanilla JS + Phoenix JS client, token auth)
  │  WebSocket (Phoenix wire protocol, ?token=beryl-demo)
Server (Gleam)
  ├── Mist HTTP — static files, /api/rooms
  ├── Mist WebSocket transport — on_connect validates token
  ├── beryl app-side dispatch — room:* routing in update
  ├── beryl groups — "public" group → general, random, help
  └── beryl presence — online users + typing indicators
```

### Channel events

| Direction | Event | Purpose |
|---|---|---|
| Client → Server | `new_msg` | Send a chat message `{text}` |
| Client → Server | `typing` | Start typing indicator |
| Client → Server | `stop_typing` | Stop typing indicator |
| Server → Client | `new_msg` | Broadcast message `{text, username, color, type, timestamp}` |
| Server → Client | `phx_reply` (push ref) | Reply to a client push — used for both delivery acknowledgment (`status: "ok"`) and validation errors (`{code, error}` payloads) via `ReplyOk` |
| Server → Client | `presence_list` | Updated online user list |
| Server → Client | `typing` | Typing indicator update |

## Collaborative CRDT Docs

**Source**: [`examples/collab_docs`](https://github.com/tylerbutler/beryl/tree/main/examples/collab_docs)

A collaborative document editor where clients merge block state locally with a
CRDT and use beryl as an unordered realtime transport.

```bash
just deps
cd examples/collab_docs && gleam run
# Open http://localhost:8002 in multiple browser tabs
```

### What it demonstrates

| beryl feature | How it's used |
|---|---|
| **Segment wildcard topics** | `document:*:*` routes each tenant/document pair inside `update` |
| **Join-level auth** | The join payload must carry an HMAC-signed tenant token |
| **Unordered realtime transport** | `BroadcastFrom(topic, "doc_state", ...)` fans out document updates while the CRDT handles merge convergence |
| **Late joiner cache** | The server returns cached merged state in the `AcceptJoin` reply |
| **Validation replies** | Invalid topics reject with `RejectJoin`; invalid sync payloads reply on the push ref |
| **Conflict resolution UI** | Concurrent edits to the same block render explicit conflict cards with all versions |

### Architecture

```
Browser (vanilla JS + Phoenix JS client + lattice CRDT packages)
  │  WebSocket (Phoenix wire protocol)
Server (Gleam)
  ├── Mist HTTP — serves HTML + static files
  ├── beryl app-side dispatch — document:*:* routing in update
  ├── document cache — merged state for late joiners
  └── beryl BroadcastFrom — fan-out of CRDT updates
```
